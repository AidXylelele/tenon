# Research: Web Console

The decisions in force, with their sources. Docs paths are under `apps/web/node_modules/next/dist/docs/01-app/` (Next.js 16.4.3).

## R1. Data flow: Server Components, Server Actions, route refresh

- **Decision.**
  - Pages read in Server Components through `libs/data-access`.
  - Writes are Server Actions that return a result, which `useActionState` or `useTransition` shows. The page then calls `refresh()` from `next/cache`.
  - Live views call `router.refresh()` on an interval.
  - No client data library is added.
- **Why.**
  - `refresh()` "refetch[es] the current route's RSC Payload without invalidating cached data", and it is used when the view depends on state outside the cache (`03-api-reference/04-functions/refresh.md`). The console caches nothing: `fetch` is not cached by default, and `cookies()` makes every route dynamic (`01-getting-started/08-caching.md`).
  - `router.refresh()` re-fetches the data and re-renders the Server Components. It merges the result "without losing unaffected client-side React … or browser state" (`03-api-reference/04-functions/use-router.md`).
  - A client library (SWR, TanStack Query) is what the docs name for "a shared browser cache … interval polling, request deduplication" (`02-guides/client-side-data-fetching/index.md`). The console needs polling only. The router does it with the reads the page already has, so one data path remains.
- **Cost accepted.** Each refresh re-runs the page's reads. Those are one to four API calls, and only while something is in flight.

## R2. Tiers: two spaces, no features or operations yet

- **Decision.**
  - Spaces: `identity`, for 001's bounded context, and `automation`, for 002's.
  - The shared frames form a `shell` space.
  - Code that only one space uses stays in that space's `__shared_context`: the draft-document model, the outline, and the vocabulary of phases and statuses.
  - The design system, the API client, live refresh and the document text are libs, because none of them knows the business.
- **Why.** Under the constitution, a feature is UI and logic "repeated across domains", and an operation is logic repeated across domains (Web Rules › Feature, Operation). No such reuse exists yet, and modules of one space may share through `__shared_context`. Creating features now would add Playgrounds and Cypress suites for code that only one space uses (IX, Simplicity).

## R3. Session: the API's cookie, held by the BFF

- **Decision.** Sign-in posts the credentials to `POST /auth/session` from a Server Action. The action reads the API's `Set-Cookie` (`name=token; Max-Age`) and stores `name=token` in the console's own cookie:
  - name: `console_session` (`__Host-console_session` under HTTPS);
  - attributes: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` in production;
  - `Max-Age`: the API's value.

  `libs/data-access` sends the pair back as the `Cookie` header. A password change, which rotates the session, stores the new pair the same way.

- **Answers that end the session.**
  - On a 401, data-access redirects to `/sign-in?next=<url>&reason=ended`. `proxy.ts` passes the URL to the app in a request header, as the docs prescribe for passing data from Proxy ("use headers").
  - Without the cookie, Proxy redirects console routes to sign-in. This is the optimistic check of `02-guides/authentication.md`.
- **Why.**
  - The API's cookie carries the absolute expiry; its idle timeout is kept server-side (`@nestjs/authentication` `SessionService.issue`), so the pair never needs a refresh between sign-ins.
  - `cookies().set` works only in Server Functions and Route Handlers (`03-api-reference/04-functions/cookies.md`). Sign-in and the password change are the only places that set the cookie, and both are actions.
  - `unauthorized()` needs `experimental.authInterrupts`, so it is not used.
- **CSRF.** Server Actions compare `Origin` with the host (`02-guides/server-actions.md`). The API's origin check sees no browser `Origin` on server-to-server calls.

## R5. The builder: one draft document, forms that keep what they do not know

- **One draft.** The draft is the document as JSON. The forms and the YAML view edit the same value. Switching views serializes the draft or parses the text; text that does not parse keeps the last valid draft and shows the error at its line.
- **Forms keep what they do not know.** A form writes only the properties it owns, so a construct the forms do not cover is kept as it is (FR-005). A task whose kind has no form is an "advanced" task, edited as YAML in its card.
- **Problems are located.** The check runs 600 ms after the last edit, as a Server Action over `POST /workflows/check`. Its problem's pointer is matched to the deepest task whose pointer is a prefix, and then to that task's field with the longest prefix. In the code view, the pointer becomes a range (`libs/document-text`).
- **Version.** Editing loads the current version and proposes the next patch number. A refusal with `workflow.version-taken` proposes the next one again.
- **Secrets.** A call's authentication picks one of the author's secrets. The builder adds the name to `use.secrets`, because the check refuses an undeclared one.

## R6. Security headers

- **Decision.**
  - `proxy.ts` sets a per-request CSP nonce, using the code of `02-guides/content-security-policy.md`, with `script-src 'self' 'nonce-…' 'strict-dynamic'`.
  - `style-src 'self' 'unsafe-inline'` is kept. React writes server-rendered `style` attributes, sonner and Radix set styles at run time, and a nonce covers neither. Scripts stay nonce-bound, and React escapes all output, so no markup can be injected.
  - `next.config` `headers()` sends HSTS, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` and `frame-ancestors 'none'` (`03-api-reference/05-config/01-next-config-js/headers.md`).
  - `poweredByHeader: false`.
- **Cost.** A nonce makes every page dynamic. Every console page is dynamic already (R1).
- **What is never kept.** Secret values and webhook URLs pass through actions and are never stored: the URL is shown once from the action's result.

## R7. Live views (superseded by R14)

- **Decision.**
  - Intervals: 1.5 s on an instance page; 2 s on lists, deliveries and recent instances.
  - A run's page refreshes only while the run has not ended. Lists, recent runs and deliveries always refresh: every 2 s while something they show is in flight, otherwise every 5 s, because a new run or delivery can appear at any time (found on the running stack: a delivery made right after the page opened never showed). Every view pauses on `visibilitychange` while hidden.
  - The view shows "Live · updated n s ago" and a dot that pulses while a refresh runs.
- **Why.** SC-003 allows two seconds. Pausing a hidden tab is FR-019.

## R8. Look and feel

- **Theme.** Light or dark follows the system preference (`prefers-color-scheme`) through Tailwind's `dark` variant, so no theme library and no flash.
- **Look.** shadcn's neutral palette with the Geist fonts already in the app. Status colours are kept for phases only: running is blue, waiting amber, completed green, faulted red, suspended violet, cancelled grey.
- **Times.** Times are formatted in the browser, in the person's locale and time zone, as a relative time with the exact time in a tooltip. The server sends ISO strings.
- **Navigation.**
  - Every route segment has a `loading.tsx` skeleton, so a dynamic route shows its frame at once (`02-guides/instant-navigation.md`: a layout that reads `cookies()` blocks navigation unless the read sits behind Suspense).
  - The console frame reads the session inside its own Suspense boundary.
  - `useLinkStatus` marks the clicked navigation item.

## R9. The official TypeScript SDK: its types, not its runtime

- **Decision.** The console imports `@openworkflowspec/sdk` (the same `1.0.3-alpha8` as the API) for its types only, as a dev dependency. The builder's task templates are written as `Specification.*` values (`satisfies Specification.CallHTTP`, …). They become the draft's JSON in one function (`newTask`).
- **Why the types.** They tie every task the builder adds to the standard's own model at build time. On the first run they caught two templates whose lists were looser than DSL 1.0.3 allows. A type-only import puts nothing in the bundle.
- **Why not the rest.**
  - **Validation, `Classes` and builders.** On import, the SDK compiles the whole schema with Ajv (`new Ajv({ schemas: [workflow] })`, which generates code through `new Function`). In the browser that needs `script-src 'unsafe-eval'`, which the CSP refuses (R6), and it adds about 600 KB plus Ajv to a route that must open fast (SC-002).
  - **The check stays with the API.** It is the platform's (002 FR-003), and it covers what the schema does not: the subset, references, expressions, secrets. A second check in the console would be domain validation outside the API (constitution I, BFF) and could disagree with it.
  - **YAML.** The SDK reads YAML through js-yaml, which reports no source positions and does not bound aliases. `yaml` gives the line of a problem and bounds aliases.
  - **`buildGraph` and Mermaid.** Its graph has no edges for `when`, `try`/`catch`, retries, `for` and `compete`, and draws a phantom `switch` edge (verified on 2026-11-02). The run line reads the document's own nesting, which is exact.

## R10. Critic round 1 (2026-11-03)

An independent review of the tiers, the BFF rules and security found no import that breaks the tier graph.

**Fixed:**

- an open redirect through a tab or a newline in `next` (`returnPath` now resolves the path as a browser does);
- the two pages that were prerendered without a CSP nonce (`connection()`);
- the idempotency key lost when an input is changed and then restored (one key per distinct start);
- `Infinity` from a form number;
- filter rows keyed by position;
- refreshes stacking on a slow API (a tick skips while one is in flight);
- the network cause shown to the person;
- a malformed `%` escape in a route giving a 500 (`segment()` makes it a 404);
- route pages owning the phase vocabulary.

**Argued against:**

- **Declaring a picked secret in `use.secrets` (R5) is authoring, not validation.** A person who picks a secret in a form has said which secret the call uses. The builder writes the document that says so, as an editor adds an import. The check stays the API's and still refuses an undeclared name in code.
- **Hiding the controls a phase does not allow, and the 1 MiB pre-check, are UX.** The API still refuses both: a 409 and a 413. The console only avoids offering what would fail.
- **The tier graph is reviewed, not linted.** The owner decided on 2026-10-28: "people review architecture". The constitution's lint clause and CODEOWNERS predate that decision for the whole repository, and the gap is recorded here.

## R11. The canvas: React Flow, laid out by the document's own structure (layout superseded by R16)

- **Decision.**
  - The builder and the run view draw the workflow with `@xyflow/react` (React Flow 12): custom nodes, custom edges, pan, zoom, fit, mini-map, and connections dragged between handles.
  - Positions come from a deterministic layout of the document's structure (`__shared_context/canvas/graph.ts`). Lists run left to right. Containers hold their lanes. Jumps arc above the line.
- **Why React Flow.** It is the canvas library of the React ecosystem, MIT licensed and maintained. n8n's editor uses its Vue counterpart.
- **Why not a layout library.** React Flow's layout guide (reactflow.dev/learn/layouting/layouting):
  - dagre "currently has an open issue that prevents it from laying out sub-flows correctly if any nodes in the sub-flow are connected to nodes outside the sub-flow", and every `for`, `try` and `fork` is a sub-flow;
  - d3-hierarchy "assigns the same width and height to all nodes";
  - elkjs is about 1.4 MB, and the guide says "we don't often recommend elkjs".

  The DSL is a structured program, so its syntax already fixes where each step goes: a sequence, branches stacked, a body inside its loop. A layered layout algorithm would only rediscover that, and could reorder it.

- **What a connection is.** An edge is drawn only for what the DSL says:
  - the next step;
  - a case of a `switch`;
  - a task's `then`;
  - the end of the run.

  Dragging from a step, or from a case's handle, to a step of the same list writes `then`. Deleting that edge removes it. No connection merges branches or crosses lists, because the DSL has none (002 spec: "without n8n mechanics").

## R13. Critic round 2: the canvas (2026-11-03)

**Fixed:**

- **`then: exit`.** At the root it now draws an edge to the end. Inside a block it marks the step as leaving the block.
- **A choice without a default case** now shows where _no match_ goes (its own `then`, or the next step).
- **Case writes.** The case name is escaped as a pointer token. A case keeps its position in the document, so a broken item before it cannot shift the handle.
- **The height of a choice** now holds its cases.
- **Fork branches** can no longer be connected to each other: a `then` between concurrent branches would mean nothing.
- **A hidden canvas** gets its first view when it gets a size.
- **One tab stop per node**, and Space no longer scrolls the page.
- **Live refresh is cheap.** An equal document is not laid out again, the canvas state and a run's progress are memoised, and `progressOf` takes one pass.

**Known limits:**

- **A green connection means "both ends ran", not "the choice took this path".** The task records do not say which case a `switch` took or which `then` a run followed.
- **The run canvas reads the first 500 task records**, as the timeline does.

## R14. Refreshing as Grafana does (iteration 3)

- **Measured** on the production build, one page left open for 30 s (`pw/requests.mjs`), per minute:

  | Page          | Browser → console | Console → API |
  | ------------- | ----------------- | ------------- |
  | Overview      | 600               | 152           |
  | Workflow page | 192               | 62            |
  | Runs          | 840               | 62            |
  | A running run | 520               | 202           |

- **Why so many.**
  - `router.refresh()` empties the router cache, so every link on the page loads its target ahead again: 2 refreshes and 54 prefetches in 10 s on Runs.
  - Lists, the Overview and a workflow's page refreshed every 5 s forever.
  - Each refresh read everything again: the user, the immutable version document, events behind a closed tab.
- **Grafana's way** (grafana.com docs):
  - "By default, Grafana does not automatically refresh the dashboard". A picker beside the refresh button sets an interval, and "Auto" derives it from what is shown.
  - `min_refresh_interval` "prevents users from setting the dashboard refresh interval to a lower value"; "the default interval value is 5 seconds".
  - Panels load lazily: Grafana "will not issue any data queries for panels that are not visible".
- **Decision.**
  - One refresh control per live page, in the page header:
    - refresh now;
    - Auto, Off, 5 s, 10 s, 30 s, 1 min, 5 min;
    - "Updated n s ago".

    The interval is kept for the viewer in browser storage.

  - **Auto.** Every 5 s while something the page shows is in flight, every minute otherwise; Off for pages with nothing live (a finished run). A tick never stacks on a refresh in flight. A hidden page waits and refreshes on return if a tick fell due.
  - **Lazy reads.**
    - A run reads its events only on its Events view (`?view=events`).
    - A workflow reads its versions only on its Versions tab.
    - A version document, which never changes once published, is fetched with `cache: 'force-cache'`. The cache key holds the session cookie, so nothing crosses sessions.
  - **Links in tables and lists** load ahead on hover, focus or touch only: Next's documented hover-triggered prefetch (`prefetch={active ? null : false}`).
- **Kept from R1/R7.** Server Components and `router.refresh()` stay. A client cache (TanStack Query, SWR) would move every live view into client components for no fewer requests: the count comes from the cadence and the prefetches.

## R15. Navigation and small screens (iteration 3)

- **Problem.** Eight destinations in three groups, two more at the foot, and technical names (Subscriptions, Event tester, Supported standard). Nothing said where a page sits, and on a phone the menu was only a drawer.
- **Decision.**
  - **Destinations.** Five, without group headings: Home (`/`), Workflows, Runs, Connections, Credentials.
  - **Connections** is one page with tabs: Webhooks (start workflows from other apps), Notifications (subscriptions: tell other apps what happened) and Test event. Routes move under `/connections/*`.
  - **Settings** is one page with tabs: Account, Team (administrators) and Standard (the conformance statement). Routes move under `/settings/*`.
  - Old addresses redirect permanently (`next.config.ts` `redirects`).
  - **Breadcrumbs** (shadcn `breadcrumb`) head every page below Home: Workflows › sales › lead-pipeline › Run 3f2a.
  - **Desktop.** The sidebar collapses to icons (shadcn `collapsible="icon"`), and canvases open with it collapsed.
  - **Phones.** A bottom bar carries the five destinations, as native apps do. A canvas opens its panel as a bottom sheet (shadcn `drawer`, vaul).

## R16. The canvas laid out by ELK (iteration 3; replaces R11's layout)

- **Problem.** R11's own layout drew jumps and skipped cases as arcs, so connections crossed containers and each other. Its fit view of a long line was unreadably small, and large workflows lost their structure.
- **Decision.** `elkjs` lays the graph out with the layered algorithm, as Microsoft's Logic Apps designer does for the same constructs (scopes, conditions, switch, for each). Its `libs/designer/src/lib/core/graphlayout/elklayout.tsx` uses:
  - `org.eclipse.elk.layered`;
  - direction `DOWN`;
  - `hierarchyHandling: INCLUDE_CHILDREN`;
  - model order kept.

  Here:
  - **Direction.** Top to bottom by default; left to right at the viewer's choice, kept in browser storage.
  - **Containers.** `do`, `for`, `try`, `fork` and catch handlers are compound nodes. `INCLUDE_CHILDREN` lays them out with the edges that leave them, which is dagre's open issue in R11.
  - **Edges.** Orthogonal routing with rounded corners. ELK places the labels, so cases and jumps never overlap. The document's order is kept (`considerModelOrder: NODES_AND_EDGES`).
  - **Collapse.** Every container collapses into one node ("4 steps"), kept per viewer and workflow. A run opens the containers that hold a running or faulted step.
  - **`try`** is its protected steps, then a rose "If it fails" container joined by a dashed failure edge. The retry policy reads on its header ("Retries 3 times, 1 s apart").
  - **A `try` around one step**, whose `catch` only retries or does nothing, is drawn as that step with a badge ("Retries 3×", "Continues on failure"). This is n8n's node setting: "Retry On Fail: when an execution fails, the node reruns until it succeeds"; "On Error, Continue".
  - **Readable first view.** 100 % from the start of the flow; Fit is a button.
  - **Loading.** ELK loads with the canvas only, as a split chunk, and lays out off the render.

- **Notes.** A step's note is `metadata.note`. The DSL's task `metadata` is free-form, so the note travels with the document and its versions. It shows under the step's name, as n8n's "Display note in flow" shows a node's note "as a subtitle". The workflow's `document.summary` shows on Start.
- **Not free placement.**
  - Positions would live in the document, and every insertion would need a person to re-place the steps.
  - A list's order is its execution order, so a picture placed by hand could contradict it.
  - Logic Apps and Power Automate lay out the same constructs automatically.

  The viewer organises the picture with direction, collapse and notes; an author organises the workflow with sections (`do`) and by moving steps up and down.

## R17. The step panel and the code editor (iteration 3)

- **Problem.**
  - A long code or JSON field stretched the panel past the screen.
  - The panel was one long form.
  - Code had no highlighting.
- **Panel.**
  - A fixed column: a header (icon, name, kind, actions) over a body that scrolls.
  - On desktops it is resizable with shadcn `resizable` (react-resizable-panels), and the width is kept.
  - Sections as tabs, after n8n's node Parameters and Settings:
    - **Settings.**
    - **If it fails.** Stop the run, continue, retry N times S seconds apart, or handle with other steps. Each choice writes a `try` around the step:
      - stop: no `try`;
      - continue: `catch: {}`;
      - retry: `catch.retry` with a constant delay and an attempt limit;
      - other steps: `catch.do`, which turns into a full `try` container.

      The step keeps its name inside the `try`, and `then` moves to the `try`.

    - **Data.** Input, output, export, `if`, timeout.
    - **Note.**
  - Actions: move up and move down within the list, duplicate, delete.
- **Code.**
  - CodeMirror 6, already the code view's editor, with `@codemirror/lang-javascript` and `@codemirror/lang-python`.
  - Line numbers, auto-indent, Tab to indent, bracket matching and closing, search.
  - Syntax errors are taken from the language's parse tree and marked as lint diagnostics.
  - A fixed height with its own scroll; "Expand" opens the same editor in a large dialog.
  - "Format" for JavaScript only, with Prettier (`prettier/standalone` with its Babel and ESTree plugins), loaded on first use. Python has no formatter of note that runs in a browser.

## R18. Failures a person can act on (iteration 3)

- **Found on the running stack** (`failure-probe/probe.mjs`):
  - a script that throws completed with an empty output;
  - a call refused by the outbound address policy said only "The service could not be reached";
  - retries happened but the record showed one row, running and then faulted.

  The runtime's side is in 002 (research there); runs survive a restart of the API.

- **Console.**
  - A step being retried shows "Attempt n · next try in s s", and the last failure in its panel. The task record's `attempt`, `retryAt` and `previousError` come from 002.
  - A faulted run's strip says what failed (title, detail), at which step (a click selects it), and what to do: Open in editor (authors) and Run again.
  - Restart is named "Run again": it starts a new run of the same version with the same input.
- **Not yet.** Continuing a faulted run from its failed step, as AWS Step Functions' redrive does. `@nestjs/workflows` can retry a failed instance from its journal (`WorkflowClient.retry`). The runtime, though, ends a DSL fault as a completed engine run, so the change is the runtime's and the domain's, to be designed with the owner first.
